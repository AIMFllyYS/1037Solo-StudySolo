## 一、核心判断

**项目适合采用“同一仓库、内容与业务代码分层、以一节课为单位提交原子内容包”的模式，不需要先重做文章系统，也不需要为了分离而立即拆成两个仓库。**

现有 `content/` 正文、JSON 题库、统一 Markdown 指令、学科注册表、板块能力声明和静态页面生成已经构成可复用基础。主要缺口不是“缺少文章页面”，而是尚未把这些能力组织成一个可机器校验、可重复提交、可安全自动发布的内容协议。补充需求进一步表明，目标应是“多格式课堂资料系统”，不能只优化 Markdown 文章系统：PDF／HTML 笔记、原始音频和 PPT 需要各自的阅读路径。

建议抓住四件事：

1. **一次课堂是一组关联内容，不是一篇孤立文章。** 原始录音、纪要、笔记、课件／详解与题库共享课堂身份；纪要与笔记独立，笔记的 PDF／HTML 是同一逻辑内容的不同格式。
2. **固定板块保持不变，课时下面组织材料子项。** 文件树支持按课堂查看全部材料；学科差异通过内容规则与阅读器配置体现，PPT 已有视觉版式时不要求改写为组件文章。
3. **自动合并只适用于受控的内容 PR。** 新组件、渲染规则、加载逻辑和工作流变更必须走独立代码 PR；不能因文件名是 Markdown 或位于注册表目录，就默认安全。
4. **闭环终点是线上可用，不是 Git 合并。** 正文、题库、资源、导航和检索索引必须来自同一发布版本；发布失败能够恢复旧版本并给出明确反馈。

本文将“现状事实”“设计建议”“待确认事项”分开。源码是当前实现的主要证据，旧 SOP、README 与源码不一致时不直接沿用旧说明。

## 二、项目目前真正具备什么

### 2.1 分类已经统一，但能力并不相同

标准分类由 [category-templates.ts](../../../lib/content-data/category-templates.ts) 统一声明，顺序是教材、详解、课上录音、课堂纪要、考前模拟、实战演练。

| 现有板块 | 当前能力 | 对本次方案的意义 |
|---|---|---|
| `textbook` 教材 | 例题、测验、检索；按章推导题库键 | 权威知识结构，不应每次录音都自动重写教材 |
| `detail` 详解 | 例题、测验、检索、媒体；按章节号推导 | 适合跨课堂沉淀的系统讲解，不适合直接当讲次容器 |
| `recording` 课上录音 | 例题、测验、检索；按录音条目推导 | 已是一次课堂内容聚合的合适入口 |
| `summary` 课堂纪要 | 检索；文章布局 | 适合这节课的结构化笔记，与录音整理稿配对 |
| `kaoqian-moni` 考前模拟 | 只读资料布局，无测验能力声明 | 当前模拟卷文章不等于交互式题库 |
| `shizhan-yanlian` 实战演练 | 只读资料布局，无测验能力声明 | 不能默认向这里放 JSON 就能开始答题 |

“真题”“模拟题”“课堂生成题”还应有来源性质的区分。自动生成的随堂题不应因为进入某个板块，就被命名成真题。当前显示名称和路由 ID 均应保留，本文不建议重命名导航。

`CategoryId` 在类型层是 `string`，可以表达学科私有板块；这只是底层扩展能力，**不意味着让内容 Agent 自由创造顶层分类**。[types/content.ts](../../../lib/types/content.ts)、[layoutProfile.ts](../../../lib/content/layoutProfile.ts) 已把内容能力和页面布局分离，应沿用这一机制。

### 2.2 录音—纪要已经有单点声明，但还不是完整内容包

[recordings.ts](../../../lib/content-data/recordings.ts) 的 `LectureMeta` 已有 `id`、`title`、`summaryTitle`、`hasSummary`、`status` 和源文件名。`recordingItems()`、`summaryItems()` 从同一声明生成 `rec-XX`、`sum-XX`。

它能解决“录音与纪要各手写一份注册”的问题，但尚未统一表达：真实上课日期、学期实例、源材料内容哈希、音频引用、题库关联、跨章节关系、内容版本、产物完整性与发布状态。`status` 默认 `done`，也不是自动审核通过的证据。

当前课堂内容的实际组合为：

```text
lib/content-data/{subject}-lectures.ts       讲次声明
        └─ manifest.ts → recording / summary 条目

content/{subject}/recording/rec-XX.md         清洗后的课堂文字稿
content/{subject}/summary/sum-XX.md           结构化课堂纪要
content/quiz/{subject}/rec-XX.json            这一讲的交互题库
content/examples/{subject}/recording/rec-XX/ 可选例题文章
```

**概率论例题是例外**：加载器对概率论不加学科前缀，因此录音例题应由现有解析规则得到 `content/examples/recording/rec-XX/`，不能照搬其他学科路径。普通录音正文和题库仍有概率论学科前缀。现有一致性校验对概率论例题根目录主要检查 `chNN`，不能把该校验通过当作录音例题已完整校验。[loader.ts](../../../lib/content/loader.ts)、[categoryKeys.ts](../../../lib/content/categoryKeys.ts)、[check-registry-consistency.ts](../../../scripts/check-registry-consistency.ts)

正文只有放文件还不够：[loader.ts](../../../lib/content/loader.ts) 读取 Markdown 前检查条目是否已注册；[page.tsx](../../../app/[subject]/[category]/[id]/page.tsx) 从 manifest 生成静态路由，且 `dynamicParams = false`、`revalidate = false`。因此未注册内容不能指望线上自动发现，已发布内容变化也需要进入新的构建发布。

### 2.3 存量数据说明：页面可用不等于每讲闭环完整

以下是本次只读统计：录音／纪要计数排除 `stub`；题库计数仅表示相应 `rec-ID.json` 文件存在，不代表内容质量合格。

| 学科 | 已注册非占位录音 | 非占位纪要 | 对应录音题库文件 |
|---|---:|---:|---:|
| 概率论 | 15 | 15 | 13 |
| 大学物理 | 25 | 25 | 25 |
| 有机化学 | 20 | 19 | 0 |
| 近现代史纲要 | 10 | 10 | 10 |
| 毛概 | 12 | 12 | 12 |
| 大二上八门学科合计 | 0 | 1 | 0 |

五门已有录音的学科共 82 个录音条目，60 个对应题库文件。概率论缺少 `rec-13`、`rec-14` 题库；有机化学 20 个录音条目都没有同名题库。这里的“缺少”仅相对于用户本次提出的完整内容包目标，不能据此判定存量内容违反旧约定。

特别需要防止两个迁移错误：

- **讲次 ID 不等于教师实际课次。** 近代史和化学的历史注册中已有 ID 与标题课次不一致的情况。不能根据标题数字重新编号，否则旧链接和题目来源都会变。
- **纪要不一定来自一条录音。** 生化已有 `sum-01`「生化讨论课笔记」，但尚无录音条目。新建生化第一讲时直接派生 `sum-01` 会冲突。应先登记独立纪要归属，保留原文与原 URL，不能自动覆盖。[modern-history-lectures.ts](../../../lib/content-data/modern-history-lectures.ts)、[chemistry-lectures.ts](../../../lib/content-data/chemistry-lectures.ts)、[biochemistry-extras.ts](../../../lib/content-data/biochemistry-extras.ts)

### 2.4 可视化基础已经存在，作者规范还需要机器化

现有渲染链支持 GFM、KaTeX／化学公式、定义／定理／例题／易错提示、推导、图片、记忆卡、时间线、比较、因果关系以及已注册视频和交互组件。[plugins.ts](../../../lib/markdown/plugins.ts)、[remarkDirectives.ts](../../../lib/markdown/remarkDirectives.ts)、[指令注册](../../../components/shared/directives/registry.ts)

因此，“按前端组件规范写文章”的方向正确。但需要区分三层：作者写的语法（如 `:::definition`）、解析后的内部标签（如 `callout`）、实际 React 组件。内容 Agent 应只使用版本化的作者语法，不应直接猜内部组件名或生成 JSX。

当前 `::video`、`::interactive` 会查已注册资源；引用不存在时可能显示“即将生成”，而非让构建失败。自动内容 PR 需要把这种情况前移为校验失败，而不是以页面能打开为验收依据。[MediaEmbed.tsx](../../../components/shared/directives/MediaEmbed.tsx)

### 2.5 默认构建还不足以充当发布门禁

[package.json](../../../package.json) 的 `prebuild` 已含编码、导航生成、注册一致性、公式字符、部分媒体与 SVG 检查和代码测试；**没有执行 `test:content`，也没有执行 `build-index`**。这不是说默认构建完全不检查内容，而是它不保证“本次课堂内容包”完整。

本次检查结果：

- `node --import tsx scripts/check-registry-consistency.ts`：0 错误、94 警告。
- `recordings.test.ts`、`quiz.test.ts`、`categoryCapabilities.test.ts` 三个测试文件：1,870 项通过、0 失败。
- 警告包含历史孤儿内容／例题／题库及元数据缺省，不能简单解释成 94 个发布故障。
- 未跑完整生产构建、全量测试、浏览器视觉验收或远端发布，因此不声称整个系统已通过上线验收。

自动化新门禁应对**新增／修改内容实行严格规则，对历史遗留问题设置精确基线**，不能为这次闭环要求一次性修复全部旧数据，也不能借“历史有警告”放行新问题。

## 三、内容板块与代码板块应该怎样分开

### 3.1 分开的是职责和权限，暂时不必分仓

建议继续同仓，以便一次 PR 的元数据与正文一起审查、一起构建、一起回滚。

| 层 | 负责什么 | 日常课堂 PR 是否允许 |
|---|---|---|
| 工程说明 | 本文、SOP、组件语法说明，位于 `docs/` | 不应成为每次同步必改项 |
| 内容正文／制品 | Markdown、受控 HTML 笔记、PDF、PPT 引用、例题、题库 JSON | 允许，按各格式独立验证，限制到本次课堂 |
| 内容元数据 | 课堂 ID、日期、关联、资源引用、版本 | 允许，使用严格数据 schema |
| 平台代码／策略 | 路由、加载器、组件、schema、学科能力白名单、工作流 | 不允许自动混入内容 PR |
| 派生产物 | 导航、检索索引、构建资源 | 由可信生成程序产出，不能由模型自由编辑 |
| 原始素材 | 音频、原始 ASR、源课件、带个人信息的材料 | 默认在私有来源存储；仓库只存批准发布部分与引用 |

注册表在语义上往往属于内容元数据，但目前载体是 TypeScript，仍然具备执行代码的能力。**“只允许改 lectures.ts”不是充分的安全边界。**

### 3.2 两个阶段，不把迁移和日常生产绑死

**短期兼容：少量注册变更 + 内容正文。**

对已有录音学科，旧式 Markdown 同步仍可继续追加 `*-lectures.ts` 声明，添加整理稿、纪要和 `rec-ID.json`；但这只能作为兼容入口，不能宣称已覆盖用户要求的 PDF／HTML 笔记和 PPT。多格式资源与课堂子树须先经一次代码能力接入。任何 import／构建之前，要由可信规则确认 TS 差异只包含允许的数据字面量，没有新 import、函数调用或可执行表达式。做不到这一点，就暂时保留注册表变更人工审核。

对大二上学科，需要一次性把 recording／summary 接入既有 `sophomoreCategories()`，或从 skeleton 改为有料填充；此类首次挂载属于基础设施／接入代码 PR。不能让每次课堂同步都修改中心 manifest。

**推荐目标：日常 PR 只含数据，注册由构建程序派生。**

可新增一个内部元数据目录，例如 `content/_meta/lectures/{subject}/{lectureUid}.json`；每课一文件。可信加载／生成程序验证后，转换成现有 `ContentItem` 与讲次列表，再复用现有 manifest、路由和组件。

这是**建议的新目录与能力，目前不存在**。接入时需要同步调整注册一致性校验的内部目录识别、文件跟踪、打包排除和 schema 验证规则，不能只创建目录就假定现有应用会读取。内部元数据也不应自动进入全文索引或以静态资源公开。

长期保留两套手工元数据是最差状态。应明确迁移边界：旧条目继续走旧注册，新条目走新数据源；适配器合并时强制检查复合键冲突。某批旧数据完成迁移后，原手工声明只保留必要兼容映射，不再双写。

### 3.3 为什么暂时不推荐独立内容仓库

独立内容仓库能提供更强权限隔离，但也引入“代码版本支持哪些内容语法”“两个仓库如何固定版本”“内容 PR 合并后哪个仓库发版”等额外问题。对于当前预算与单项目同步需求，同仓分层成本更低。

当以后存在多个前端共用内容、大量独立作者或严格访问隔离需求，再考虑拆仓。届时必须由应用版本固定一个内容版本，不能构建时无条件拉内容仓库最新分支。

## 四、最重要的新契约：一次课堂内容包

### 4.1 先固定每种产物的语义

按用户补充，正常课堂有四类学习材料；课件如果与详解不是同一份材料，应另列而不是混为一个资源：

| 逻辑角色 | 展示方式 | 自动出题用途 |
|---|---|---|
| 原始录音 `recording` | 音频播放／来源访问；配套有时间戳的逐字稿 | 是：使用可追溯到录音的逐字稿或音频分析结果 |
| 课堂纪要 `minutes` | 独立短文，便于快速回顾本课议题／重点 | **否**：不作为自动出题输入或题目唯一依据 |
| 整理笔记 `notes` | 同一篇笔记提供 HTML 阅读版与 PDF 版 | 是：使用这一逻辑笔记的一份标准文本表示 |
| 详解 `explanation` | 有 PPT 就按 PPT 资料展示，也可保留已有文章形式 | 默认不加入本次自动出题输入 |
| 课件 `slides`（若独立提供） | 直接保留幻灯片阅读体验，提供原文件 | 默认不加入本次自动出题输入 |
| 定向题库 `quiz`（平台派生） | 课时级“本课练习”，复用现有题库与答题组件 | 产物而非来源 |

原始录音和逐字稿是不同格式／角色关系：音频是来源，逐字稿是用于阅读、检索和出题的可追溯表示，不能把清洗后的文字稿冒充音频原件。现有大一文字内容保持原标签／来源说明，不凭空补写音频存在。

课堂纪要与整理笔记必须独立：前者是速览，后者是较完整的学习材料。整理笔记 PDF／HTML 则共享一个 `resourceUid` 与语义版本，不能分别注册成两套出题来源、两篇重复知识。HTML 适合屏幕阅读，PDF 适合固定版式、打印与下载；若实际 HTML 版式在手机上不适用，可由用户切换 PDF，而不是声称任意 HTML 都天然响应式。

若“详解 PPT”就是教师课件，保存一个资源，声明它具备课件／详解用途；如果详解是另外制作的 PPT，则是两个资源。两者都能按课时挂载，同一份资料也能在既有详解板块通过引用被找到，不复制正文。

教材保留教材版本边界，既有详解文章不被录音自动改写。**接受 PPT 作为详解内容载体，不再要求详解一定是重新撰写的 Markdown 或可视化组件。**

### 4.2 身份不能只用“第几讲”或文件名

建议拆开以下概念：

- `subjectId`：学科稳定 ID。
- `courseInstanceId`：具体学期／课程实例，区别于当前 `freshman-2` 等学年展示分组。
- `lectureUid`：首次识别课堂时分配的稳定身份，后续整理、补图、修题不变。
- `displayOrder`：展示次序，可以调整，不决定身份。
- `recordingItemId`／`summaryItemId`：现有路由 ID；旧 ID 保留，新 ID 可使用学期／日期／短唯一后缀组合，仍遵守现有安全标识符规则。
- `revision`：该课堂内容包的内容版本；修订递增，不再创建“另一节课”。

同一个来源哈希只能说明字节相同，不能独自充当课堂身份：一次课可包含多个录音分段，ASR 重跑后文字也可能变化。应先按来源系统稳定记录 ID 或人工确认映射归属课堂，再用有序来源清单及哈希识别变化。

新增讲次不得用“当前最大编号 + 1”处理并发。补录一节旧课不应导致后续 URL 集体重排；同一日期两次课也不能合并成一条。

### 4.3 元数据至少需要覆盖的字段

以下为建议字段职责，不是当前 `LectureMeta` 已支持的接口；第一阶段不必立刻做成复杂平台。

| 字段组 | 最小内容 | 用途 |
|---|---|---|
| 协议 | `schemaVersion`、作者语法／渲染契约版本、学科规则版本 | 阻止新内容使用旧前端不支持的组件 |
| 身份 | 学科、课程实例、课堂 UID、显示顺序、日期与来源时区 | 防重、排序、跨学期隔离 |
| 版本 | `revision`、`baseRevision`、`bundleHash` | 防覆盖、增量修订与重复检测 |
| 来源 | 来源 ID、有序分段、各段摘要哈希／完整文件哈希、时长、访问级别 | 可追溯且不泄露本机路径或凭据 |
| 产物 | 录音、逐字稿、纪要、笔记、课件／详解、题库的角色、资源 ID、格式、路径／对象引用、哈希 | 精确列出本次提交的完整集合 |
| 多格式 | 一个逻辑资源的 PDF／HTML／PPTX 等表示及共同内容版本、生成器版本 | 避免重复注册、重复出题、预览与原件混代 |
| 用途 | `searchable`、`quizEligible` 与可阅读性分别声明，受平台策略约束 | 纪要可阅读／检索但禁止用于自动出题 |
| 关系 | 教材版本／章节引用、其他课堂引用、学科附加资源引用 | 防止把“课堂”误绑成“一章” |
| 质量信息 | 待核实片段、教师重点依据、补充说明标识、允许缺失原因 | 支持真实性审核与有意义的失败反馈 |
| 权限 | 可公开／限课程／私有、来源使用许可状态 | 决定能否进入仓库与索引 |

一个路径不是任意字符串：校验器应从身份与角色推导允许路径，拒绝越界、绝对路径、`..`、符号链接逃逸、大小写冲突及额外文件。路径规范要在 Windows 与 Linux 上一致。

`bundleHash` 应按规范化后的内容、来源版本与产物清单计算；排除执行时间和自身哈希字段，明确排序、UTF-8 与换行规则。单纯重跑不能因为新 `generatedAt` 或 JSON 键顺序变化就产生一份新 PR。

来源时间戳最好表达为 `{sourceId, segmentId, startMs, endMs}`。仅写“12:30”在多段录音中有歧义；PDF 引用需要页码，PPT 引用需要幻灯片号，HTML 引用需要稳定章节／块锚点。题库当前 `sourceRef.path`＋`label` 可先继续使用，把结构化证据放在 sidecar，后续再升级 UI。定位点应同时绑定资源版本，防止修订后第 8 页已不是原来的内容。

**规则与报告由不同权限方维护。** 学科规则不能被本次内容 PR 降低要求；作者填写的“已校验”只是声明，发布门禁必须自行执行验证，不能信任内容包附带的成功标记。

### 4.4 完整性是显式策略，不是空文件占位

对于本次目标，建议完整课堂包要求原始录音引用及可用的来源文本、独立纪要、笔记 HTML／PDF 两种交付、已提供的详解／课件及其可用预览，以及非空定向题库和来源。真实没有课件时允许明确标注未提供，不制造假课件；来源访问权限未具备、已声明的某格式文件缺失或题目未完成时，不能报成完整发布。

如果只有逐字稿、没有足够信息出题，应标为待补齐并留在草稿 PR，不能用纪要替代笔记、用两份不一致的 PDF／HTML 拼装完成状态，也不能通过写空题库、捏造题目或把 `hasSummary` 改成 false 绕过要求。

历史课堂可以保留“只有文字稿／无音频／无纪要／暂无题库”等兼容状态，新管线从启用日期开始严格执行。独立讨论课笔记也应允许作为独立资源，不强行虚构对应录音。

### 4.5 同一课堂的修订与题目历史

新课堂默认“一课一 PR”；同一课尚未合并时的补充更新同一个 PR，已发布后的修订创建指向相同课堂 UID 的新修订 PR。

`baseRevision` 必须等于目标分支当前内容版本。发现别人已修订时停止覆盖，重新比较；不得依靠模型“看起来差不多”自动解决语义冲突。删除／撤回、修改课堂归属、重写既有答案，应升级审核等级。

当前答题状态按学科／题库键保存，恢复主要检查 question ID 重合率，达到 50% 就尝试恢复；不是按题干、答案和题库版本匹配。[quiz.ts](../../../lib/stores/quiz.ts)、[quiz-progress.ts](../../../lib/quiz-progress.ts)

所以自动更新题库时不能把旧 `q001` 改成另一道题而继续复用 ID。建议实质换题分配新题目 ID，文字修正保留 ID 但更新内容指纹；之后加入题库版本／题目指纹匹配的会话迁移或失效提示。旧成绩保留当时版本，不应无声地用新答案重新解释旧作答。

### 4.6 推荐的文件树：课时文件夹下放资源，而不是四套平行课次

**建议采用用户提出的“课时 → 材料子项”。** 在现有课上录音／课时入口内，以一次课堂为文件夹；固定学科分类不增加一套平行结构。示意如下，标题与 ID 为设计示例：

```text
组织学与胚胎学
├─ 教材
├─ 详解                         按主题浏览，引用同一份详解资源
├─ 课上录音／课时               沿用现有入口，名称可另定
│  ├─ 第 01 课 · 上皮组织
│  │  ├─ 原始录音               播放音频；可切到逐字稿
│  │  ├─ 课堂纪要               独立速览，不参与出题
│  │  ├─ 整理笔记               阅读器内切 HTML / PDF
│  │  ├─ 课件                   PPT 阅读，若独立提供
│  │  ├─ 详解                   可为另一份 PPT
│  │  └─ 本课练习               只基于录音与笔记
│  └─ 第 02 课 · ……
├─ 课堂纪要                     如保留：跨课汇总入口，指向同一纪要
├─ 考前模拟
├─ 实战演练
└─ 其他资料                     学科独立资料；有内容才显示
```

不建议再把“整理笔记”设成一个文件夹，并给 HTML、PDF 各建一层文件节点：它们是同一资源的格式切换，嵌套增加点击成本，也让题库来源容易重复。需要显式文件视图时可以在资源面板列出原文件和下载项，而不是增加主要导航深度。

这里必须区分**导航树、物理目录、内容身份和访问路由**。左侧有文件夹不等于 URL 必须变成五层，也不要求立即搬动历史文件；新的材料可继续使用 `/{subject}/{category}/{resourceItemId}` 这种三段路由，只要资源 ID 在该命名空间内唯一。父课时用单独的 `lectureUid` 聚合子资源。

### 4.7 文件树已有的能力与真正需要改的地方

桌面 [FileTree.tsx](../../../components/layout/FileTree.tsx) 已递归渲染 children；[FileTreeItem.tsx](../../../components/layout/FileTreeItem.tsx) 将有 children 的节点作为展开／收起文件夹。由此判断，**这一交互方向可复用现有实现**，不是从零造导航。

但以下接缝需要一次代码建设，不能仅添加 children 后宣告完成：

1. **文件夹不是文章。** 现在静态路由生成会枚举父节点；应明确哪些是只展开的组、哪些有课时总览页，不要让纯文件夹变成空正文页面。若要点标题进入总览、点箭头展开，也需显式设计交互。
2. **子项不是同一种材料。** 现有树把父级 subject／category 传给所有后代；新结构需要资源角色、格式及实际目标引用。文件图标、选中、高亮、预取与面包屑要按真实目标解析。
3. **跨分类入口是引用，不是复制。** 保留旧 `summary/sum-XX`、`detail/...` 的 canonical 地址，新课时树用引用节点指向它们。当前 `ContentItem` 没有这种导航别名契约，需要补充 `targetRef` 等概念，或生成等价的导航投影；不能给每个板块复制一份文件。
4. **移动端不是完全递归。** [MobileChapterPicker.tsx](../../../components/layout/MobileChapterPicker.tsx) 主要是分组＋直接子项；“课时＋材料”的一层嵌套可以作为目标，但若再加学期／笔记格式层就需升级。加载器和分块器也要统一遍历，不能只测桌面树。
5. **练习绑定课时，而不是当前材料文件名。** 当前 `category-item` 用 item ID 直接得到 quizId。若当前叶子是 `...-minutes` 或 `...-notes`，它会推导出不同题库；需要显式 `lectureRef`／`quizRef`。旧 `rec-ID.json` 可以保留，一个课时共用同一套题。
6. **先跟随引用，再推导展示能力。** 否则放在 recording 目录下的纪要会继承 recording 的测验能力，和“不根据纪要出题”的规则混淆。有效能力要由材料角色与课堂关系计算，不只看父 category。

推荐采用“课堂／资源为唯一数据，左树与跨课汇总为派生视图”。旧路径适配、导航、详情页、来源引用和索引都指向同一资源，不长期维护两套课堂数据。

## 五、多格式阅读与文章规范：不要把所有资料改写成组件

### 5.1 建立小而明确的作者契约

建议建立一份面向内容生成器的版本化规范，包含：文件布局、允许的 Markdown／指令、属性类型、有效组件 ID、媒体路径规则、正确示例、禁止写法和错误提示。schema、示例与校验器应同步维护，不能只靠一份长提示词。

对确实由 Markdown 创作的内容，第一阶段建议允许标题、段落、列表、表格、公式、带图注图片、既有提示块与少量已验证指令，**不引入 MDX 或任意组件代码**。也不应假设 YAML frontmatter 已有解析支持：当前共享插件链没有此能力，先使用 sidecar 元数据更清晰。

这份作者规范只管 Markdown 内容，**不作为 PPT／PDF 的重写要求**。用户已经收到的 HTML／PDF 笔记应按制品接入，不要求再生成一份人工排版的组件版文章；PPT 保留幻灯片结构。

增加新可视化组件时走独立代码 PR，包含实现、语法、sanitize 规则、渲染映射、测试和示例；代码上线并确定支持版本后，内容 PR 才可引用。禁止先放 `::interactive{id=未来组件}` 并把占位显示算成完成。

当前 Markdown 已有 `rehype-sanitize`，不能把旧渲染文档未写 sanitize 解读成“项目没有消毒”。但独立 `renderType: html` 走 `srcDoc` iframe，现有沙箱同时允许 scripts 与 same-origin，并非同一信任边界，**不应直接作为自动生成 HTML 的可信安全入口**。[plugins.ts](../../../lib/markdown/plugins.ts)、[sanitizeSchema.ts](../../../lib/markdown/sanitizeSchema.ts)、[ContentPageClient.tsx](../../../app/[subject]/[category]/[id]/ContentPageClient.tsx)

用户需要的 HTML 笔记应支持，但分两级：静态 HTML 默认禁脚本、清理危险标签／属性并限制外部资源；确有交互需求时，只允许审核过的渲染模板／固定运行时，置于隔离来源，默认无父页面权限、表单、弹窗或任意联网。任意自带 JavaScript 的 HTML 转人工审核，而非整个 HTML 格式都被拒收。阅读正文不授予改业务代码或读取应用存储的权限。

### 5.2 不让统一模板抹平学科差异

建议在新生成的整理笔记中保留共有信息骨架：本次主题、学习目标、核心概念、教师明确重点及来源、易错点、练习入口和延伸材料；然后按学科选择适用模块。没有课堂问答就省略问答，不为了满足模板硬编；没有必要的图就不用图，不以“组件数量”判断质量。**以下表格是笔记与题目生产的学科策略，不是要求把已有 PPT 拆解重做的转换清单。**

| 学科 | 课堂笔记重点 | 首先复用的表达方式 | 定向题目重点／附加资源示例 |
|---|---|---|---|
| 概率论 | 条件、随机变量、分布与推导的适用范围 | 公式、推导块、分布图、易错提示 | 条件辨析、建模计算；公式对照、补充证明 |
| 大学物理 | 研究对象、模型假设、方向、单位和推导 | 公式、示意图、推导、现有交互 | 模型选择、量纲与计算；实验演示、补充习题 |
| 有机化学 | 结构、立体关系、反应条件、机理步骤 | 化学公式、结构图、比较块 | 产物判断、机理、异构辨析；谱图与反应条件表 |
| 近现代史纲要 | 时间顺序、因果、人物／事件／概念边界 | 时间线、事件卡、比较与因果块 | 史实辨析、材料分析；史料、专题对照 |
| 毛概 | 概念体系、理论语境、教材版本和论述结构 | 概念卡、比较表、记忆卡 | 概念辨析、材料分析；易混概念与论述框架 |
| 医学英语 | 术语、词根词缀、句法、语篇与语境 | 双语表、精读注释、词汇记忆卡 | 阅读／翻译／术语应用；词表、听力素材 |
| 仪器分析 | 原理、仪器链路、条件、谱图和误差 | 原理图、公式、谱图图片、比较表 | 方法选择、参数解释、数据分析；仪器手册与谱图集 |
| 系统解剖学 | 方位、毗邻、层次、结构命名与识别 | 有标注来源的图片、比较表、术语卡 | 识图、结构关系、名词；图谱索引、实验观察 |
| 医学统计学 | 研究设计、变量类型、方法前提、结果解释 | 方法决策表、公式、数据与图表 | 检验选择、结果判读；数据字典、软件输出案例 |
| 细胞生物学实验 | 原理、步骤、观察、对照、记录与误差 | 流程图、观察表、图片、注意事项 | 操作逻辑、对照设计、现象解释；实验记录模板 |
| 医学细胞生物学 | 结构—功能、调控过程与实验证据 | 示意图、过程讲解、比较与记忆卡 | 机制理解、实验结果推断；机制图与实验资料 |
| 组织学与胚胎学 | 组织鉴别、染色／倍率、发育阶段 | 标注图、鉴别表、发育时间线 | 组织识别、形态比较、时序；切片图谱与观察记录 |
| 生物化学与分子生物学 | 反应、代谢路径、调控、能量与实验逻辑 | 通路图、公式、比较、概念与记忆卡 | 代谢关联、调控和实验判读；通路对照、讨论课资料 |

这些是依据学科内容性质提出的生产规则建议，不是已核实的本校各科考试大纲。具体题量、题型比例、术语版本和教师重点应由实际课程资料确定，不能从旧物理试卷的“100 分／固定配比”推广到所有课。

图上点击标注、音频跟读、动态谱图等新交互，若当前没有组件实现，先用图片＋编号问答等已有能力替代。对结构图／切片／实验数据，资料不足时应标缺项；不能自动造图后把示意图当作真实观察证据。

### 5.3 学科配置应有，但不要造十三套系统

建议把配置拆成“学科默认规则＋课程实例覆盖”：学科决定惯用模板、术语与组件能力；课程实例决定教材版本、实际考试要求、教师重点和学期安排。

平台代码负责渲染机制，配置负责选择能力，文章负责传递知识。一个学科没有某种资源，就不强制生成；一个组件适用于多个学科，就复用而非复制。新学科接入需要一次元数据注册和规则选择，之后正常同步不应再改路由或组件。

### 5.4 真实性需要比“JSON 能解析”更强的检查

自动出题输入应由可信程序按角色选取：**原始录音的可追溯逐字稿／音频分析结果＋整理笔记的标准文本，排除课堂纪要**。PDF 和 HTML 两个笔记版本只取同一逻辑笔记的一份内容，避免重复放大；课件／详解不因放在同一文件夹就自动混入题目来源。该选择规则不可由内容 PR 自行覆盖。

题目范围应来自本节课，但题干应自洽，不写“老师刚才说的那个是什么”。解析应解释知识依据，不用“老师说了所以正确”替代论证。项目已有物理录音题质量规则，可以抽取通用部分，再保留学科专属规则。[physicsRecordingQuality.ts](../../../lib/quiz/physicsRecordingQuality.ts)

若笔记与录音冲突，保留差异并标为待核，不让另一份纪要充当自动裁判。每题须引用允许的源角色与版本；校验器拒绝仅引用纪要的题目。纪要修改不触发重新出题，笔记排版／PDF 导出更新也不应触发；录音或笔记知识内容变化才使题库进入待重验状态。这里需要内容指纹与文件哈希分开管理。

“纪要不出题”不等于不能从纪要页面跳到已有本课练习。可以保留全课统一练习按钮，但不提供“基于本纪要生成题目”的自动入口；纪要仍可参与普通全文检索，用途权限必须区分。

需要保留三个不同的证据等级：

- 教师原话／课堂记录：能回到来源段落或音频位置。
- 整理者概括：忠于来源但不是逐字引用。
- 补充解释／纠错：明确是补充，并引用教材或其他可核对来源。

“老师明确说要考”必须有原始依据；“可能有助于复习”只能标成建议。疑似转写错误或知识冲突不能凭模型信心自动消除。对专业事实、真实图片标注及答案正确性的审查，脚本只能验证结构与出处存在，不能保证语义正确；建议初期人工抽查高风险点，成熟后仅低风险增量进入全自动通道。

### 5.5 阅读器应该按格式分发，题目入口应该与格式解耦

目前 [RenderType](../../../lib/types/content.ts) 只有 `markdown | html | component`；[loader.ts](../../../lib/content/loader.ts) 也是读 Markdown／HTML 或交给组件，没有通用 PDF／PPT／音频资源解析。已有 `fallback-pptx.py` 是抽取到 Markdown，不是保真幻灯片阅读器，不能把它算成“已经直接渲染 PPT”。

建议在概念上拆开三个维度：

- **角色**：原始录音、纪要、笔记、课件、详解，决定用途。
- **格式／阅读器**：audio、Markdown、HTML、PDF、slides，决定如何展示。
- **课堂关系**：lectureRef／quizRef，决定这节课对应哪些练习及材料。

同一资源允许多个格式，例如一份笔记有 HTML／PDF，一份幻灯片有 PPTX 原文件／PDF 预览。应用通过资源清单拿到格式与安全的资源 URL，不再把所有文件当 UTF-8 正文读取。具体是否扩展 `RenderType` 联合类型，还是增加资源视图组件，由实施时选择；必须同时覆盖 loader、路由、导航、校验与打包，不能只扩类型声明。

当前 [ContentPageClient.tsx](../../../app/[subject]/[category]/[id]/ContentPageClient.tsx) 明确在 `renderType !== 'markdown'` 时隐藏例题／测验 Tab。**如果原样使用当前 HTML 分支展示笔记，会失去现有测验入口。** 因而本课练习应作为课时级兄弟子项／公共按钮，通过 quizRef 复用现有题库；不要求 PDF／HTML／PPT 先转换成 Markdown 才能关联练习。

### 5.6 PPT：保留视觉成果，区分“按幻灯片看”与“原生演示运行”

用户的主要需求是复习课件，而非重新设计课件。因此默认不进行语义改写、不重排成组件、不强制 Manim／交互动画。需要选择的是浏览器如何呈现原有幻灯片，不能承诺把 `.pptx` 文件地址直接放进当前 iframe 就能显示。

| 路线 | 优点 | 成本／限制 | 建议 |
|---|---|---|---|
| PPT 原文件＋预先导出的 PDF 预览 | 保留固定版式；能复用笔记 PDF 阅读器；提供原件下载 | PDF 是静态预览，不保留原生动画／触发交互，字体与转换效果需检查 | **优先用于以复习为主的课件／详解** |
| PPT 原文件＋逐页图片预览 | 静态页面效果便于控制，适合缩略图／快速翻页 | 图片文字不可直接选择检索；需要独立文本层，图多时存储／流量增加 | 复杂页面补救或缩略图，不必每份同时生成多套全尺寸预览 |
| 经授权的在线 Office 演示嵌入 | 更接近原生演示体验，少做本地渲染 | 第三方可用性、账号／分享权限、移动端和离线兼容，具体效果需实测 | 必须保留动画／在线演示时再评估 |
| 自建 Office 渲染服务／全面 PPTX 浏览器解析 | 可进一步控制部署 | 运维、授权、兼容性、字体与大文件处理成本高 | 不作为当前有限预算下的首期前提 |

Microsoft 明确说明 PowerPoint 导出 PDF 会固定格式和布局，适合不安装 PowerPoint 的查看；PDF 不是原生幻灯片播放。因此推荐方案应标为“PPT 课件（PDF 预览）”，不能把静态预览宣传成原生 PPT 渲染。[Microsoft：PowerPoint 导出 PDF](https://support.microsoft.com/en-us/powerpoint/training/save-powerpoint-presentations-as-pdf-files)

PDF 阅读器可以评估 PDF.js，提供缩略图、翻页、缩放、页码、搜索和全屏；它是 PDF 的显示层／查看器，不是 PPTX 解析器。首期也可以使用受控 PDF 嵌入＋下载兜底，但必须测试手机表现，不能只测桌面浏览器。[Mozilla：PDF.js](https://mozilla.github.io/pdf.js/getting_started/)

PowerPoint for the web 官方嵌入方案依赖 OneDrive 文件与分享设置；本次不建议为了“可嵌入”改变课堂材料可见范围，也不把受限文件 URL 直接传给第三方预览服务。采用外部在线演示时须先核对许可、权限和资源可用性。[Microsoft：嵌入演示文稿](https://support.microsoft.com/en-US/PowerPoint/embed-a-presentation-in-a-web-page-or-blog)

若采用静态预览，优先让现有本地材料整理流程导出预览后随内容包交付，避免每次云端构建都要求安装 Office。转换只是格式处理，不是模型重新写课件。云端负责验证 PPT 原件哈希与预览的派生关系、页数和必要页面抽样；转换失败时不拿旧 PDF 冒充新 PPT 的预览。

需要检查中文字体、公式、图表、遮盖关系、隐藏幻灯片、批注／演讲者备注的发布选择。动画步骤对知识理解至关重要时，要保留原文件并提示静态版缺失，或选在线演示／逐步帧导出；不得悄悄丢失后继续标“完整”。未提供真实样例 PPT 前，本文不承诺特定转换器能完整保真。

### 5.7 看的是原文件，检索／出题用的是可追溯文本

不重写 PPT，并不意味着不能抽取文本。建议为每份可搜索资源准备一份**机器读取侧文本**，保留幻灯片号、PDF 页码、HTML 块锚点或音频时间戳，绑定源资源哈希；它服务检索和引用，不成为另一份强迫用户阅读的文章。

当前索引只读取已注册的 Markdown。新接入的 HTML、PDF、PPT 即使在树里可见，也不会自动被完整检索。因此需在内容输入层扩展统一的“资源 → 可搜索文本”解析，保持现有检索后端边界不变。对扫描件／图像内容，只在必要时 OCR；识别失败就标出覆盖缺口，不能用生成的摘要伪装成完整抽取。

一份笔记的 PDF／HTML 只索引一个标准语义版本；PPT 与其 PDF 预览也只算一份资源。纪要可单独索引，但 `quizEligible=false`。搜索可用范围和自动出题输入范围绝不能共用一个布尔开关。

## 六、各学科的“其他板块”如何扩展同步

### 6.1 不要误用已有全局 `other` 学科

当前 `other` 是杂项学科，包含英语练习、工具、公式和规划，并不是“每个学科的其他资料”。它还被 [chunker.ts](../../../lib/ai/indexing/chunker.ts) 和 [loader.ts](../../../lib/content/loader.ts) 的部分检索／大纲流程显式排除。

因此把解剖图谱或生化实验资料都放进全局 `other`，既丢失学科归属，也可能无法按预期检索。建议保持全局 `other` 的历史用途不变。

### 6.2 固定骨架之外，只设一个受控的学科附加资料入口

若确实需要独立入口，可在该学科下增加统一含义的“其他资料”，候选 ID 为 `extras`，显示名可按实际情况定为“其他资料”或“补充资料”。**这是新增设计，当前标准分类中没有它。** 是否所有学科都展示空入口，建议不强制；有已发布内容才显示。

固定六大板块的顺序与职责不变。新资料按资源类型／标签在 `extras` 内组织，不因为来了“词表”“实验记录”“谱图”就各增加一个顶层板块。

默认文章布局、明确声明检索能力；需要交互题库时，提前配置可验证的 key 策略。因为现有题库按学科＋quizId 存储，不包含 category，附加资料若使用 `category-item` 应让 item ID 自带 `res-...` 等独立前缀，防止与 `rec-*`／`tb-*` 题库冲突。

已有 UI 类型允许 `children`，但加载器和分块器部分实现只处理到一层 children。不要把通用资源组织成任意深度树；第一阶段建议一层分组或扁平列表＋标签，后续确有需要再统一所有树遍历逻辑。

### 6.3 决定归属的规则

| 材料性质 | 主存放位置 | 与课堂的关系 |
|---|---|---|
| 原始录音及忠实逐字稿 | 课时的原始录音资源 | 核心来源，保留历史 recording 路径兼容 |
| 这节课的课堂纪要 | 课时的纪要资源 | 独立速览；summary 可保留跨课索引 |
| 这节课的整理笔记 HTML／PDF | 课时的笔记资源 | 同一笔记的两种格式，不混入纪要 |
| 本次生成的练习题 | 该课堂题库 | 课时级入口，来源只有录音与笔记 |
| 课件／详解 PPT | 课时的幻灯片资源 | 直接阅读；详解分类可引用同一资源 |
| 跨课系统讲解 | `detail` | 可以是文章或 PPT；通过引用，不自动覆盖 |
| 教材原有内容 | `textbook` | 关联到具体教材版本与章节 |
| 往年真实试卷／模拟卷 | 既有实战／模拟入口 | 标清来源性质，不混入随堂题 |
| 词汇表、图谱、谱图、实验观察、讨论资料等 | 学科 `extras` | 可关联一节或多节课，也可独立同步 |
| 一节课专用图片／音频 | 对应资源存储 | 若仅作附件，无需再制造一篇其他资料文章 |

每份资源只有一个主记录，多处通过稳定 ID 引用，避免在录音、纪要、详解和其他资料里复制同一正文。跨学科资源可以有相关学科列表，但应明确主归属，不制造多份相互覆盖的源文件。

### 6.4 扩展资源同样使用数据契约

建议独立资源拥有 `resourceUid`、`kind`、学科、标题、版本、来源、正文／附件引用、相关课堂／章节和可见性。`kind` 从受控列表选择，例如词汇、图谱、实验记录、补充资料；初期不必穷举未来类型。

未知类型进入待分类状态，不能由本地 Agent 擅自新增 category、渲染组件或目录。只要现有文章组件足够表达，就可以作为纯内容同步；需要新交互的，再升级为代码需求。

实验个人记录、真实受试者数据和受限课件不应默认公开。这个判断属于发布前内容授权与隐私审核，不能由“它在学习平台里有用”自动推导发布许可。

## 七、原始音频与大素材：与正文分离，但版本必须关联

本次查看到的课堂录音模型和指令层没有专用音频来源字段／回听协议，因此不要把文字稿接入完成等同于音频闭环完成。按用户补充，原始录音是必须保留的重要材料；具体首期采用授权外链回听还是站内播放器，仍需实施时确定，不再把它作为可有可无的学习资源。

建议将原始音频、大课件保留在私有对象存储或已授权来源系统；Git 内保留稳定资源 ID、对象版本／哈希、分段和时间戳。小型批准发布的图片可随内容进仓库，并使用固定规范路径，不提交本地绝对路径。

若要在线回听，需一次性增加媒体解析与访问控制、播放／定位能力及资源校验。短期可以展示已批准来源链接，不承诺自动跳转播放位置。持久元数据中不要保存会过期的签名 URL，也不要为了方便把私有音频改成公开链接。

外部资源不受 Git 原子提交控制。建议发布顺序为：准备不可变资源对象 → 校验可读取及哈希 → 内容 PR 引用 → 生成候选发布 → 激活发布。失败上传形成的未引用对象设置延迟清理窗口，不能提前删除旧版本资源，必须为回滚保留。

若未来构建器需要下载远程资源，应限制域名、协议、大小、重定向和私有网络目标，不能任由内容里的任意 URL 在携带凭据的环境中发起请求。`.gitignore` 也不是私密保障：已经跟踪的文件和历史提交仍需要单独治理。

## 八、PR 到线上：真正的自动化闭环

### 8.1 推荐状态与职责

```text
来源准备完成
  → 本地生成课堂内容包
  → 本地结构／质量自查
  → 创建或更新同一课堂 PR
  → 可信门禁对当前提交做校验与预览
  → 满足自动合并条件后合并
  → 以合并后的精确提交构建页面、题库与索引
  → 候选发布冒烟验证
  → 激活版本并线上复验
  → 记录课堂 UID / revision / commit / 发布结果
```

失败分别停在“内容需补齐”“校验失败”“需人工审核”“构建失败”“部署失败”等状态。合并后部署失败，状态应是“已合并、未发布”，不是重新创建相同课堂 PR。

本地负责语义整理与内容生产、已有 HTML／PDF 接收和必要 PPT 预览转换；平台规则负责机械校验；云端 Agent 可以承担现有编排，但合并资格、路径边界和上线判断应由确定性规则给出，不需要每次再让模型完整阅读全库。出题模块只接收允许的录音／笔记输入；材料角色过滤属于内容交付契约，不需要本次重构 Agent。

### 8.2 三种 PR，不能混用同一个自动合并策略

**A：常规内容 PR。** 已接入学科＋已支持资源类型／组件；只修改允许的正文、题库、元数据和资源。条件全部满足后可以自动合并。

**B：能力／接入代码 PR。** 新学科挂载、新类型、新组件、schema 变化、加载器或工作流修改。必须单独审核和验证；先发布兼容能力，再接收依赖它的内容。

**C：高风险内容修订。** 删除／撤回、跨课移动、来源冲突、大规模重写、敏感材料、既有答案实质变更。即使只有 Markdown／JSON，也需要额外审核。

不能仅凭 PR 标签、作者名称或“只改 `content/`”就放行。机器人身份可作为信号，实际 diff、文件类型、大小、变更范围和规则校验结果才是判据。权限、阈值与例外列表不得由内容 PR 自行修改。

### 8.3 必要门禁

1. **变更范围**：本课／本学科白名单，禁止代码、依赖、配置、工作流和未知额外文件；删除、重命名、二进制、符号链接单独处理。
2. **元数据与完整性**：身份唯一、版本冲突、来源清单、录音／纪要／笔记各格式／已声明详解或课件／题库齐全，文件非空，标题／路径／引用一致；原件与预览的版本对应。
3. **文章契约**：未知指令、缺少必填属性、组件引用失效、公式解析失败、图片不存在、危险链接必须报出文件与位置。KaTeX 当前 `throwOnError: false`，所以构建成功不能代替公式错误检测。
4. **题库结构与用途**：实际 JSON 运行时验证；题型与答案匹配、整数索引合法、多选去重、子题校验、分值／汇总一致、来源可解析，且来源是录音／笔记而非纪要或未授权扩展资料。现有 TypeScript 类型与测试要复用，但不能把 `JSON.parse`＋类型断言视为完整 schema 校验。
5. **语义真实性**：重点和答案抽查到来源；不确定段落升级审核；无来源时不编造。机械通过与语义可信是两个状态。
6. **全局一致性**：复用注册校验、导航派生和内容测试；除了现有文件，还验证“声明必须有的题库却没生成”等反向缺失。
7. **候选页面与制品**：展开本课文件夹，依次打开录音、独立纪要、笔记 HTML／PDF、PPT 预览与题库；看公式、关键图、窄屏表格、页数和下载权限。HTML 做安全检查；PPT 不要求出现自制组件，只检查对应格式阅读正确。初期可人工预览，之后对成熟模板自动截图测试。
8. **合并前身份**：校验绑定 PR 当前 head SHA 和对应基线；新 push／重放事件后不能复用旧成功结论。当前分支发生冲突时不自动猜测内容。

先运行廉价静态校验，再进行构建和视觉检查。共享注册／生成代码变化时跑全量内容校验；纯新增课堂可以用影响范围选择检查，但最终注册键冲突等全局不变量仍需验证。

可信校验器应来自已批准的基线或固定版本。尤其在短期允许 TS 注册修改时，不能先 import PR 提交的注册表执行代码，再检查它是否安全；PR 预检不应持有生产部署密钥或付费模型密钥。

### 8.4 GitHub 触发与权限需要实际联调

仓库本地 `.github/workflows/` 目前只看到 Supabase 保活／备份工作流，没有在本次范围内发现内容 PR 门禁及部署工作流。**这不证明你的云端 Agent 没有自动化**：它可能在仓库外。其合并条件、部署脚本、事件机制与权限目前都未验证。

GitHub 支持以必需状态检查等规则约束合并，并可限定状态来源；建议明确保护目标分支、限制绕过权限，必要时由外部可信检查服务写状态。不同仓库可见性与 GitHub 套餐的可用能力不同，实施前确认，不假设当前订阅一定包含所有规则。[GitHub：受保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

还需验证“自动 PR 是否真的触发下一环”。按本次查询的 GitHub 文档，工作流使用 `GITHUB_TOKEN` 创建／更新 PR 的部分事件会形成需批准的运行，其他事件仍有防递归限制；需要无人工批准的工作流生成 PR 场景，可考虑适当权限的独立 GitHub App 安装令牌。**不能沿用“机器人提交一定触发 CI”或“GITHUB_TOKEN 永远不触发 PR 检查”这两种笼统假设。** 本地 Agent 直接通过 API 提 PR 与 Actions 内二次提 PR 也要区分。[GitHub：GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token)

这里仅给接入要求，不创建工作流或改变账号权限。部署入口应幂等校验仓库、目标分支与准确提交，不因一条重复 webhook 就重复部署或再次出题。

## 九、最容易漏掉的一环：导航、检索索引与部署版本一致性

### 9.1 导航是派生产物，不应让模型维护两份

`nav.generated.json` 由 [gen-nav-manifest.ts](../../../scripts/gen-nav-manifest.ts) 从 manifest 生成。短期遵守当前约定，在 PR 验证前由程序重建并检查差异；中期可选择仅在构建期生成，但需要统一开发、CI 和发布行为，不能有人手改、有人生成。

当前瘦导航只保留部分字段。未来若学科自定义展示策略需要依赖新字段，必须检查导航是否保留、消费端是否使用；不能仅在内容元数据新增字段就假设 UI 会变化。

### 9.2 索引必须作为发布产物进入闭环

`content/.index/` 在 [.gitignore](../../../.gitignore) 中被忽略；[build-index.ts](../../../scripts/build-index.ts) 单独构建关键词与向量索引，上传也是显式 `--publish`。生产环境缺少有效索引时，默认不再回退全库文本扫描。[loader.ts](../../../lib/content/loader.ts)

这意味着“本地跑过 build-index，再提交内容 PR”不会把本地索引自动带上云端。云端应对**合并后的准确内容版本**构建或获取对应索引制品，并与页面产物一起部署。

建议记录发布描述：应用提交 SHA、内容包版本集合、内容摘要、作者契约版本、索引格式／模型／维度、资源版本清单。索引哈希只覆盖其可搜索输入，并不能代表题库、非搜索资源和全部页面；需要额外的发布级摘要绑定整体产物。

本次仅核对索引的输入／产物／健康状态边界，不改变 Agent 搜索执行逻辑。

### 9.3 现有健康检查与低成本模式的两个细节

[indexHealth.ts](../../../lib/ai/search/indexHealth.ts) 已有文件／向量尺寸／模型检查和 `contentHashMatch`。但内容哈希不匹配时主要打警告，最终仍可能 `ok: true`。自动发布必须检查 `contentHashMatch === true`，不能只检查 `ok`；未知值或跳过哈希检查也不能当作同步完成。

另一个需要在实施时处理的边界：现有 `--bm25-only` 分支会通过 `finalizeVectors()` 按 chunk ID 保留缓存向量，该分支没有逐个验证缓存文本哈希。因此它不能被直接解释成“新正文和所有保留向量已经一致”。

低成本方案可以先保证当前版本关键词检索，再增量补齐向量，但必须有明确的索引模式和覆盖率；变化 chunk 的旧向量应失效或在该模式禁用，且运行端能识别降级。未完成这个适配前，不宜仅凭 BM25-only 命令成功就判定完整混合检索发布成功。

### 9.4 发布与回滚是整套版本切换

候选版本应在独立目录／产物中完成检查，避免边运行边覆盖内容和索引。切换后用本次课特有关键词检查检索，用实际题库 API 检查学科／讲次与题量，用关键资源检查可访问性。

部署失败保留旧版本。线上回滚应同时恢复代码、内容、索引与资源版本引用，而不是只执行代码回退；索引和搜索状态存在进程缓存，应切换到新进程／明确失效，不依靠替换文件自动刷新。

两个 PR 连续部署时，应防止较旧提交的慢任务在较新版本上线后再激活。若合并多个内容 PR 批量发版，最终回执要告诉每个课堂版本属于哪次发布。

本文的最小闭环以 Web 上线为准。Electron 安装包是否随每次内容 PR 更新是另一条发行策略；不能把 Web 部署成功写成所有桌面安装都已更新。

试点覆盖的不只是“新建成功”：

| 场景 | 必须观察到的结果 |
|---|---|
| 新增一节正常课堂 | 一课一文件夹，录音、纪要、笔记、课件／详解、题目各有正确入口 |
| 切换笔记 HTML／PDF | 同一资源与版本，不重复注册／索引／出题 |
| 只修改课堂纪要 | 不触发自动重新出题；已有题库仍关联该课 |
| 只调整笔记排版 | 更新格式制品，不因文件哈希变化重复生成题目 |
| PPT 原件更新 | 预览同步更新；旧预览不能通过版本检查；无强制组件改写 |
| 纪要混进自动出题源 | 可信输入过滤／来源校验拒绝 |
| 手机打开课时子项 | 可以展开并选择所有材料，题库不因 HTML／PDF 格式消失 |
| 原样重跑／重复事件 | 不创建第二节课，不制造无意义 PR，不重复付费生成 |
| 一节课有两段录音 | 仍是一个课堂包，时间戳能定位具体分段 |
| 补录旧日期课堂 | 展示排序正确，既有 ID 不重排 |
| 缺纪要／缺某笔记格式／缺题库／引用失效 | PR 留在未完成状态，不自动合并 |
| 夹带代码或降低校验规则 | 内容通道拒绝，转独立审核 |
| 修订与其他提交冲突 | 检测 `baseRevision` 不匹配，不覆盖新内容 |
| 旧答案发生实质变化 | 不把旧答题状态无声套用到新题 |
| 页面更新但索引落后 | 发布不能宣告完整成功 |
| 部署失败或任务乱序 | 旧版本继续可用，旧任务不覆盖新发布 |
| 生化新增首讲 | 既有讨论课 `sum-01` 正文与 URL 保留 |

### P3：验证后再推广学科附加资源

## 十一、预算、异常与仍需确认的边界

预算优先花在课堂语义整理、来源核对与题目质量上；路径推导、JSON 生成、哈希比较、注册和发布判断由程序完成。云端无需重复出题或重写笔记。

建议设置每课生成预算、最大重试次数、网络退避及人工接管条件；重复事件先查课堂 UID／版本／包哈希。校验失败返回具体文件、题号与规则，优先修复失败产物，不重做全部课堂。向量采用可验证的增量缓存，视觉验证只覆盖本次变化及必要回归页面。

本次没有调用费用计量接口，因此不声称实际消耗了多少美元，也不能保证未来每课同步的 API 成本。未调用子智能体或付费嵌入／出题服务。

实施前仍需确认，但不影响上述架构结论的事项：

1. 云端当前究竟在哪运行、如何接收 PR、是否已有外部 CI、部署采用哪种产物；本次未连接远端验证。
2. 仓库／站点是否公开，课堂录音、教师材料和图谱的分享范围是什么；权限不明时不自动扩大公开范围。
3. 原始音频首期采用外链回听还是站内播放器＋时间戳定位；PPT 是否要求保留动画，或可接受明确标识的 PDF 静态预览。
4. 每节课希望的题量与题型，是否允许资料不完整时仅保留草稿；默认完整发布不接受缺项。详解 PPT 与课件是否同一份，以实际交付文件判定。
5. 各学科实际教材版本与考试要求，以及“其他资料”入口是否需要统一名称。
6. Web 内容更新与 Electron 内容更新是否分开管理。
