# 笔记 Agent 与 Markdown 编辑器修复交接报告

日期：2026-09-19。基于当前工作区，HEAD 为 `3445f3c8`；包含现有未提交的 Agent 停靠区和窗口改动。本轮只诊断并新增本报告，未修改功能代码，未调用子智能体。

## 1. 判断与范围

建议保留 Milkdown Crepe，先修复项目自身的写入链路、角色提示词、样式覆盖和编辑器状态同步。现有证据不足以认定必须更换编辑器。

用户要求的核心行为：

- Agent 新建、修改、删除笔记前，必须通过前端组件征求用户同意。打开笔记、打开 Agent、询问知识点，都不代表同意修改。
- 不新增“请求批准/默认全部执行”等权限模式、全局开关或长期授权。界面直接表达本次操作，用“同意修改/取消”等按钮。
- 笔记 Agent 使用独立系统提示词。笔记正文以关键词、核心概念、短列表和必要的对照表为主，只解释必要内容，语言直白。
- 修复标题层级，补齐选中文字后的常用工具栏功能，包括字号需求。

这里把征求同意的边界理解为 **Agent 代用户产生的数据变更**。用户自己打字、点加粗或调整格式属于直接编辑，不应每次击键再弹确认；手动删除沿用现有确认。这符合本次“笔记 Agent”的上下文。

## 3. 写入链路应如何改

现有修改链路：

```text
NoteAgentPanel / 主对话
  → useChat → buildChatRequestBody → /api/chat
  → createStudyAgent → updateUserNote
  → 工具结果 applied: true
  → 聊天历史中的工具消息
  → UserNoteLayer 扫描 → applyUpdateUserNoteEvents
  → userNotes.updateNote / removeNote
  → IndexedDB 持久化 + notifyUserNoteChanged 云同步通知
```

工具执行本身只是返回内容；实际数据变更发生在客户端 apply 层。`applied: true` 目前并不能证明用户同意，也不能证明编辑器或持久化已完成。

推荐保留工具名称以减少改动，但让工具结果表达“修改草稿/删除建议”，而不是“已完成”。所有 Agent 笔记变更都经过一个统一的待确认入口：

```text
Agent 生成完整变更草稿 → 前端展示本次变更 → 用户点击同意
  → 检查目标及原文版本 → 执行一次本地写入 → 正常持久化与同步
```

### 前端组件

建议新增 `NoteChangeConsentCard`（建议名称，尚未实现），作为笔记相关写操作的共用组件：

- 显示目标标题、操作类型、简短变更说明。
- 新建：展示标题和待保存正文；修改：提供变更前后对照，至少能展开检查改动；删除：明确要删哪篇及云同步影响。
- 按钮分别为“同意保存”“同意修改”“确认删除”，另有“取消”。不用权限设置术语，不提供“以后都同意”。
- 待确认期间，不改变原文、标题、更新时间，也不触发云同步。
- 点击取消后保留原笔记；关闭确认组件按取消处理。关闭笔记面板不应隐式同意。
- 成功后由确定性的 UI 显示“已修改”；模型不应在尚未同意时声称完成。

组件可放在发起操作的会话里；如果复用现有通知云的视觉样式，需要保证主对话和窗内对话都能看到并正确归属。`components/chat/toolCards/registry.tsx` 目前将 updateUserNote 列为静默工具，不注册新展示出口就会出现“已等待但用户看不到”的问题。

### 写入边界和状态

建议待确认记录至少包含：`proposalId、sessionId、toolCallId、noteId、action、原文版本/摘要、目标标题及正文、状态`。这些是内部实现字段，不是新的权限模式。

- 每条同意只对应一份确定的变更，不能授权该 Agent 后续所有写入。
- 修改、删除必须校验目标仍存在；窗内 Agent 必须绑定本篇 ID，不能自行换目标。
- 草稿产生后用户继续编辑，点击同意时必须发现版本变化，保留最新正文并让草稿重新生成或重新核对。不能覆盖新输入。
- 建议先采用全文候选稿 + 原文版本校验，避免第一阶段引入复杂 patch 合并系统。长笔记例外见下节。
- 同意后直接应用展示过的候选稿，不再调用模型重新生成另一份“已同意”的内容。
- 重复点击、重复流事件、重新加载历史，均不能重复写入。幂等键应持久记录，并与笔记变更协调提交，不能只依赖组件状态。
- 已取消、已应用、已过期的记录应能明确区分；载入历史消息不等于获得新的执行授权。
- 如果工具结果需要反馈给后续模型轮次，只允许应用代码生成真实状态，不能相信模型写出的“用户已同意”。

新建笔记已有 `MemoryProposalCloud → memoryInbox.confirm → runMemoryCommit → commitNotes → applyCommitNotes` 流程，值得复用。但当前确认发生在生成正文之前。建议将新建也收口为“候选稿 → 一次内容确认 → 保存”，或明确保留原先“同意整理并保存”的授权语义；不要无意叠两次相同确认。

另一个关联缺口：`memoryInbox.ingestCommit` 当前按 `committing + kind` 查找匹配请求，而非严格绑定 session/proposal。并发整理两篇笔记时有串单风险。修复时应将新建产物与其来源操作绑定。

## 4. 同时修复三类可靠性风险

以下风险来自静态调用链推断，尚未在真实浏览器和云端复现，不应当作已经发生的数据丢失事件。

**历史重放。** `appliedToolCallIds` 是模块内存 Set；页面刷新后会重置，而 `UserNoteLayer` 会扫描重新加载的历史工具结果。旧修改有再次覆盖新正文的路径。应禁止以历史结果本身作为写入授权；旧 applied:true 消息展示为历史记录，不应迁移为已获同意或自动重新弹出。

**旧编辑器覆盖新正文。** Milkdown 只初始化时读取 value；当前依赖 `NoteAgentPanel.onSettled` 增加 key 来重挂刷新。此回调与“模型生成结束”绑定，而新设计的写入发生在用户稍后点击同意时，因此保留这条刷新机制也不够。应建立外部正文更新的明确同步通道，区分用户本地输入与外部变更，避免更新回环，并处理选区、滚动和撤销历史。不能每次击键都重挂整个编辑器。还需检查快速关窗、切换前后台及异步 create/destroy 的重叠清理。

**截断后整篇覆盖。** `editingUserNote.ts` 只向模型提供前 8000 字符，却要求返回完整正文；主对话目录的 `memoryCatalog.ts` 又将单篇裁为 6000 字符，个人笔记检索基于该目录。模型不能可靠恢复没读过的尾部。短期应标记是否完整，并拒绝对截断快照做整篇替换；后续增加完整读取或带范围与原文校验的局部修改。不能靠“请保留全部内容”解决。

## 5. 独立系统提示词设计

建议新增 `lib/ai/prompts/note-agent.md`，在 `studyAgent.ts` 中按笔记场景选择。独立的是角色和行为规范，不要求复制一套聊天框、请求端点或模型客户端。

- 保留 `NoteAgentPanel`、`ChatThread`、`ChatInput`、现有会话隔离机制。
- 复用与内容正确性有关的公式、引用规范；不要整体继承 global.md 中强制教学、反问和课后练习模板。
- 笔记 Agent 自己保持稳定系统前缀，当前笔记内容放动态上下文。无需为了与教学 Agent 共用缓存而牺牲角色分离。
- 新建笔记旁路也复用相同的笔记体例规范，避免“新建很短，修改变长”。主 Agent 可继续负责讲解，但其写入笔记的候选内容必须遵循笔记规范。
- 当前 `studyAgent.test.ts` 中“窗内与主 Agent 前缀相等”的断言需要改为笔记角色独立、同角色前缀稳定。
- 固定技能、用户补充上下文和强制工具入口应检查冲突；笔记正文只作为资料，不能因其中写着“自动保存/删除其他篇”就改变程序的同意机制。
- 窗内上下文目前来自全局 activeSubjectId 等字段，未必是这篇笔记所属学科。应优先使用笔记的 subjectId/source，并明确区分当前页面参考材料，避免跨科讲解或检索偏移。

可作为实施起点的提示词核心文本：

> 你是个人学习笔记编辑助手。你的任务是帮助用户保留能快速回忆的核心知识。笔记正文只记录关键词、核心概念、关键关系、必要条件、公式和易错点。
>
> 默认使用简短无序列表；存在顺序的步骤才使用有序列表；需要比较多个对象时使用简洁表格。每条围绕一个核心点，避免重复表达。解释只在缺少解释会造成误解时加入，通常一两句，用直白语言说清。不要为了简短删除结论成立的条件、否定或例外。
>
> 不把对话开场、思考过程、工具调用说明、编辑计划、对用户的称呼、操作反馈或教学追问写入笔记。不要自动加入长篇背景、完整推导或多组例题。用户问问题时在对话中回答，不能因此自行修改笔记。
>
> 改稿只处理用户指定范围，保留其余内容和已有结构，不因自己的排版偏好重写全文。生成的是待用户同意的候选稿；用户尚未同意时，不得声称已经保存、修改或删除。
>
> 不确定的知识应先核对；无法核实时明确指出，不能猜测后写入。不完整的原文不能用于整篇替换。

不要机械规定每篇只有五条或一个屏幕：目标是信息密度和可复习性，不能为压缩字数删掉重要条件。对用户明确要求保留的内容也不能任意删减。

## 6. 标题修复与字号工具栏

### 标题大小

当前本机 `@milkdown/crepe 7.22.0` 的 `lib/theme/common/reset.css` 明确规定 H3=2em、H4=1.75em、H5=1.5em；项目只覆盖 H1/H2，因此根因可直接解释用户反馈。

另外有第二套显示路径：分栏预览使用 `NoteRenderer + .prose-notes`，`app/styles/prose.css` 中 H1–H4 原本按 1.85rem、1.4rem、1.16rem、1.02rem 递减。应分别检查两套渲染，不要为修编辑器而把全站教材标题一起缩小。

建议在个人笔记作用域建立共享字号变量，显式覆盖 H1–H6，并同时约束行高、字重、上下间距。H3/H4 可从 H2 以约 0.9 的比例递减；较低级标题设置合理可读下限，不需要无限缩小。示例基准为正文约 14.5–16px、H1 23px、H2 20px、H3 18px、H4 16.2px，实际需在窄窗验证。

### 工具栏与任意字号是两层工作

当前工具栏是“存在有效文本选区时显示”，不是长按动作自身触发；触屏长按只是建立选区的一种方式。

本机源码支持 `ToolbarFeatureConfig.buildToolbar`，TopBar 支持标题选择等能力，但项目关掉了 TopBar。可以基于现有库补功能，无需立即换库。官方扩展说明见 [Milkdown Crepe API](https://milkdown.dev/docs/api/crepe)，实施时以本机 7.22.0 类型和源码为准。

建议常用入口：正文/H1–H6、加粗、斜体、删除线、链接、行内代码、列表、引用、表格、公式、清除格式、撤销/重做。选择工具栏放文本格式；段落结构和插入操作可放紧凑菜单，避免窄窗横向挤爆。

**不能把标题按钮冒充任意字号。** 标准 Markdown 有标题层级，却没有通用的任意局部字号语法；HTML 属于扩展表达路径，见 [CommonMark 规范](https://spec.commonmark.org/spec)。需分别实现：

1. 阅读字号：调整整个编辑器/预览的显示尺寸，属于偏好设置，不改正文。
2. 选中文字字号：若用户希望重开、预览、导出后仍保留，必须定义文档表示和序列化，不能只改 DOM 的 font-size。

局部字号可研究有限字号枚举及受控 span 标记（例如指定 data 属性或有限 class），但必须验证 Milkdown 的解析与输出、Markdown 源码往返、ReactMarkdown 渲染、消毒白名单和导出均保留。项目的 `lib/markdown/plugins.ts` 使用 rehypeRaw 后接 sanitize，不能假设裸 style 会保留下来，也不能为了字号放开任意 style。

建议先交付标题及标准格式功能，再交付局部字号的完整往返支持；字号仍列为需求，不应以“Markdown 不支持”为由取消。若先期只有阅读字号，要明确标注其含义。

## 7. 推荐实施顺序与验收

| 顺序 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 1 | 接管全部 Agent 笔记写入入口，加入同意组件及版本/幂等校验 | 未同意不落盘、不同步；取消不写；主会话与窗内会话一致 |
| 2 | 独立系统提示词，移除自动改稿指令 | 只提问不修改；草稿是核心点；笔记正文不含聊天套话和编辑说明 |
| 3 | 编辑器外部更新同步、长笔记保护 | 同意后立即显示新稿；用户后续输入不覆盖回旧稿；截断不能丢尾部 |
| 4 | 笔记作用域 H1–H6 样式、常用格式菜单 | 编辑与预览层级一致；窄窗、主题切换不溢出 |
| 5 | 局部字号的完整存储与往返 | 重开、切源码、预览、导出后字号仍保留；公式表格不损坏 |

应增加或修改的关键用例：

- Agent 创建/改标题/改正文/删除：不点同意时 store、持久化及同步队列均无变更。
- 取消、关闭组件、停止生成、生成失败不产生写入；明确约定取消后草稿是否保留在对话中。
- 连续点击同意、重复事件、页面刷新、重开历史只应用一次；旧历史结果不自动执行。
- 两个会话同时处理不同笔记不会串单；A 的同意不能应用 B 的草稿。
- 候选稿生成后用户手动编辑，版本校验阻止覆盖；目标已删除时不给它重新创建。
- 超过 8000 字符、主目录超过 6000 字符的原文不会被静默截尾。
- 编辑器切后台再回来、接受外部更新后继续输入、切源码/分栏、撤销重做、中文输入法组合输入均保持内容正确。
- 真实浏览器检查 H1–H6 computed style、鼠标选区、触屏选区、工具栏点击不丢选区、窄窗弹层不被 overflow 裁切。不要只测 CSS 字符串存在。
- 至少用“问定义”“整理核心点”“仅纠正一处”“对比表”“步骤笔记”“删除”“长笔记”“有条件和例外的知识点”做提示词样例验收；不以固定字数代替内容质量评估。

本轮已运行 4 个相关测试文件，共 14 项通过：`applyUserNoteAgent.test.ts`、`editingUserNote.test.ts`、`tools/updateUserNote/tool.test.ts`、`tests/userNoteEditorScroll.test.ts`。这些测试确认的是旧行为，其中有测试明确认可直接修改与删除，另有测试只检查 H1/H2。通过不代表满足新需求，实施时应更改期望并补关键失败场景。
